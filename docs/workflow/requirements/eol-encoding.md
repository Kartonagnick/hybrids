python
------
Вопрос:  
- Если скрипт python будет в кодировке utf-8 без BOM, и при этом он будет содержать русские буквы 
  (текст, который выводится в консоль, а так же комментарии к коду), могут ли быть какие то проблемы?  

Ответы:  
- Если мы говорим о Python 3, то проблем с кодировкой UTF-8 без BOM не будет.  
  Это стандарт де-факто и рекомендованный формат.  
- Если мы говорим о Python 2.7, там нужно было обязательно писать первой строкой `# -*- coding: utf-8 -*-`.  
  В Python 3 это не требуется.  

Примечание: Для Python-скриптов BOM крайне нежелателен, особенно если вы планируете запускать их на Linux:  
- Шебанг `#!/usr/bin/env python3`: если в начале файла стоит BOM, Linux не распознает шебанг, 
  и скрипт не запустится как исполняемый файл (будет ошибка `Exec format error`).  
- `Стандарты PEP 8` прямо рекомендуют использовать UTF-8 без BOM для файлов Python.

vbs
---
Вопрос:  
- Если скрипт vbscript будет в кодировке utf-8 без BOM, и при этом он будет содержать русские буквы 
  (текст, который выводится в консоль, а так же комментарии к коду), могут ли быть какие то проблемы?  

Ответ:  
- Да, проблемы возникнут практически гарантированно.  
  Движок VBScript (интерпретаторы cscript.exe и wscript.exe) не поддерживает кодировку UTF-8 без BOM  

Основные проблемы:  
- Некорректное чтение кода: интерпретатор ожидает, что файл будет в кодировке ANSI 
  (для русской Windows это Windows-1251) или UTF-16 LE с BOM. 
  Если файл сохранен в UTF-8 без специальной метки (BOM), VBScript попытается прочитать его как ANSI.  
- Искажение кириллицы (кракозябры): русские буквы в коде и строковых переменных превратятся в нечитаемые символы, 
  так как байты UTF-8 будут интерпретированы по таблице Windows-1251.  
- Ошибки выполнения: если кириллица встречается в комментариях, то интерпретатор может «проглотить» символы 
  переноса строки, из-за чего следующий за комментарием код может склеиться с ним, 
  и вызвать синтаксическую ошибку.  
- Проблемы с консолью: даже если интерпретатор прочитает файл (например, с BOM), 
  стандартная консоль Windows (cmd.exe) часто работает в кодировке CP866. 
  Без принудительной смены кодовой страницы консоли на 65001 (chcp 65001), 
  вывод кириллицы из UTF-8 скрипта все равно будет некорректным.  

Основные проблемы с LF:  
- Склейка строк: интерпретатор может не распознать одиночный символ LF как конец инструкции. 
  В результате он попытается прочитать несколько строк кода как одну длинную строку, 
  что неизбежно вызовет синтаксическую ошибку (например, `Expected statement` или `Syntax error`).  
- Игнорирование кода: В некоторых случаях интерпретатор может просто «пропустить» значимые блоки кода, 
  считая их частью предыдущей строки.  
- Проблемы с комментариями: Если строка заканчивается на LF, комментарий, 
  начинающийся с символа ' или Rem, может не завершиться. 
  Весь последующий код до ближайшего CRLF будет считаться комментарием и не выполнится.  
- Ошибка «Unterminated string constant»: Если внутри строки или после нее используется неправильное окончание, 
  интерпретатор может выдать ошибку о незавершенной строковой константе.  

Таким образом, комбинация `UTF-8 без BOM + LF` - это худший вариант для VBScript:  
- Из-за UTF-8 без BOM вы получите «кракозябры» вместо русских букв.  
- Из-за LF скрипт, скорее всего, вообще не запустится или упадет с синтаксической ошибкой в первой же строке.  

Рекомендация:  
- Для стабильной работы на Windows всегда используйте CRLF,
  и кодировку ANSI (Windows-1251) либо UTF-16 LE с BOM.  

Как сделать правильно:  
- Для стабильной работы на Windows всегда используйте CRLF.  
- Для максимальной совместимости: кодировка ANSI (Windows-1251). 
  Это стандарт для VBScript в русскоязычной Windows.  
- Если нужен Юникод: UTF-16 LE с BOM (в некоторых редакторах она называется просто «Unicode»). 
  VBScript хорошо работает с этим форматом.  
- UTF-8 с BOM: иногда работает, но часто вызывает ошибку «Invalid character» (недопустимый символ) 
  в самой первой строке из-за того, что интерпретатор не понимает метку BOM в начале файла.

wsf
---
Для .wsf (Windows Script File) лучше всего использовать UTF‑16 LE с BOM.  

Почему именно так:  
- WSF — это XML‑формат: файл начинается с XML‑декларации (например, <?xml version="1.0"?>), а XML по умолчанию ориентирован на Unicode. 
  UTF‑16 — один из «родных» для XML вариантов, и с BOM он однозначно определяется парсером.  
- Поддержка всех символов: UTF‑16 корректно отображает кириллицу, эмодзи, спецсимволы и т. д., 
  в отличие от Windows‑1251, который ограничен набором символов этой кодовой страницы.  
- Совместимость с движком скриптов: Windows Script Host (WSH),
  и связанные парсеры надежнее обрабатывают UTF‑16 с BOM в XML‑контейнере WSF.  

Чего лучше избегать:  
- UTF‑8 без BOM: WSH может некорректно определить кодировку, 
  из‑за чего кириллица превратится в «кракозябры».  
- Windows‑1251: хоть и работает в простых случаях, это не универсальное решение,
  и потенциально приведёт к ошибкам при использовании любых символов вне этой кодировки.

ps1
---
Вопрос:  
- Если скрипт повершелл (`ps1`) будет в кодировке utf-8 без BOM, и при этом он будет содержать русские буквы 
  (текст, который выводится в консоль, а так же комментарии к коду), могут ли быть какие то проблемы?  

Ответ:  
- Да, проблемы могут возникнуть, и их характер напрямую зависит от версии PowerShell, которую вы используете. 
  Основная сложность заключается в том, что разные версии по-разному интерпретируют файлы без специальной метки (BOM)  

Последствия для разных версий PowerShell:  
- Windows PowerShell (версии 5.1 и ниже):  
  - Проблема: эта версия (стандартная для Windows 10/11) при отсутствии BOM считает, 
    что файл сохранен в системной кодировке «ANSI» (в русской Windows это обычно Windows-1251).  
  - Результат: все русские буквы в строках, командах и даже комментариях превратятся в нечитаемые символы («кракозябры»). 
    Это может привести не только к испорченному выводу в консоль, но и к ошибкам синтаксиса, 
    если кириллица используется в путях к файлам или именах переменных.  
- PowerShell (версии 6.0, 7.x и выше):  
  - Проблема: отсутствует. В кроссплатформенном PowerShell кодировка UTF-8 без BOM является стандартом по умолчанию.  
  - Результат: скрипт будет работать корректно, русские буквы отобразятся правильно.  

Как PowerShell реагирует на LF:  
- Совместимость версий: и Windows PowerShell (5.1), и современный PowerShell (7.x+) одинаково хорошо понимают как CRLF, так и LF. 
  Интерпретатор корректно разделяет строки в обоих случаях, поэтому логика скрипта не нарушится.  
- Кроссплатформенность: если вы планируете запускать скрипт на Linux или macOS через PowerShell Core, 
  то использование LF является стандартом и даже предпочтительно.  

Возможные проблемы и нюансы:  
- Цифровые подписи (Authenticode):  
  Это самая серьезная техническая проблема. 
  Если вы подписываете скрипт цифровой подписью для обхода политики AllSigned, 
  изменение окончаний строк с CRLF на LF (например, при сохранении в Git или другом редакторе) разрушит подпись. 
  Система сочтет файл измененным или неподписанным и заблокирует его запуск.  
- Отображение в старых редакторах: Устаревшие инструменты (например, старый «Блокнот» в Windows 10 до обновлений) 
  могут отображать весь код в одну бесконечную строку, так как они ожидают только CRLF. 
  Современные редакторы (VS Code, Notepad++, актуальный Блокнот) справляются с этим без проблем.  
- Работа с Here-Strings:  
  Внутри многострочных строк `@" ... "@` тип окончания строки сохраняется «как есть». 
  Если ваш скрипт формирует конфигурационный файл, который строго требует CRLF, 
  а сам скрипт сохранен с LF, итоговый файл может оказаться некорректным для целевой программы.  
- Шебанг (Shebang) в Linux:  
  Если вы используете шебанг (например, `#!/usr/bin/pwsh`) для запуска скрипта как исполняемого файла в Linux, 
  строка шебанга обязана заканчиваться только на LF. Наличие `\r` (CR) приведет к ошибке «command not found», 
  так как система будет искать интерпретатор с именем `pwsh^M`  

Итог: если вы не используете цифровые подписи и работаете в современных редакторах, переход на LF не вызовет проблем.  
Однако для чисто «виндовых» окружений стандартом остается CRLF.  

Чтобы скрипт гарантированно работал во всех версиях PowerShell и корректно отображал кириллицу, рекомендуется:  
- Использовать UTF-8 с BOM (Byte Order Mark): Это явный сигнал для Windows PowerShell 5.1, что файл нужно читать как Юникод.  
- Настройка консоли: если даже при правильной кодировке файла в консоли видны «кракозябры», убедитесь, что:  
  - В коде установлена кодировка вывода: [Console]::OutputEncoding = [System.Text.Encoding]::UTF8.  
  - В свойствах самого окна консоли выбран шрифт, поддерживающий кириллицу (например, Consolas или Lucida Console).  
- Системная настройка (Windows 10/11): Можно включить в настройках системы «Бета-версия:  
  Использовать Юникод (UTF-8) для поддержки языков во всем мире», 
  тогда Windows PowerShell 5.1 начнет понимать файлы без BOM как UTF-8. 
  Однако это может повлиять на работу других старых программ.

bat
---
Вопрос:  
- Если скрипт на языке bat будет в кодировке utf-8 без BOM, и при этом он будет содержать русские буквы 
  (текст, который выводится в консоль, а так же комментарии к коду), могут ли быть какие то проблемы?  

Ответ:  
- Да, проблемы обязательно будут. Если вы просто сохраните .bat файл в UTF-8 без BOM, 
  то русские буквы в консоли превратятся в «кракозябры» (нечитаемые символы).
  А если сохранить с BOM, то станет ещё хуже: BOM — это невидимый маркер (три байта EF BB BF) в самом начале файла. 
  Интерпретатор cmd.exe не умеет его игнорировать, и воспринимает как часть первой команды.
  Вместо выполнения первой строки (например, @echo off) консоль выдаст ошибку: 
  `ï»¿@echo не является внутренней или внешней командой`.  

Основные причины:  
- Командная строка Windows (CMD) по умолчанию использует старую кодировку (обычно CP866 для русской Windows). 
  Она не понимает UTF-8 автоматически.  
- Комментарии: Даже если русские буквы только в комментариях, это может привести к ошибкам выполнения. 
  Интерпретатор может неверно считать длину строк или спецсимволы, из-за чего скрипт «вылетит» или пропустит команды.  

Как это исправить:  
- Чтобы русский текст в UTF-8 отображался корректно, в начало скрипта нужно добавить команду смены кодовой страницы на 65001,
  и переключить шрифт консоли на Unicode-совместимый (например, Lucida Console или Consolas):  
  ```
  @echo off & chcp 65001 >nul
  echo Привет, это текст на русском!
  rem Это комментарий
  ```

Проблемы с LF:  
- В отличие от современных языков программирования, интерпретатор cmd.exe плохо переваривает «линуксовые» окончания строк (LF). 
  Он ожидает стандарт Windows — CRLF (возврат каретки и перевод строки)  
- Склеивание команд: Интерпретатор может не увидеть разрыва строк и попытаться выполнить весь скрипт как одну бесконечную команду. 
  Это приведет к ошибке: «"Имя_команды" не является внутренней или внешней командой...».  
- Ошибки в циклах и условиях: В блоках if и for (внутри скобок) использование LF почти гарантированно ломает логику, 
  и скрипт просто закрывается с ошибкой синтаксиса.  
- Проблемы с комментариями: Если после rem или :: стоит только LF, следующая за ним команда может быть воспринята,
  как часть комментария и не выполниться.  

Рекомендация:  
- Всегда использовать CRLF  
- Если важна совместимость «из коробки» без лишних команд, сохраняйте скрипт в кодировке OEM 866  
- Если используете UTF-8, всегда добавляйте chcp 65001 в начало файла  
- Никогда не используйте BOM  
- Никогда не используйте LF

bash и sh
---------
Происхождение и стандарты:  
- sh (Bourne Shell) — старейшая оболочка Unix, созданная Стивеном Борном. 
  Сегодня под `/bin/sh` обычно скрывается оболочка, совместимая со стандартом POSIX (например, dash в Debian/Ubuntu).   
- bash (Bourne Again SHell) — современное «надмножество» (superset) для sh, которое включает в себя все функции оригинала,
  и добавляет множество новых возможностей («синтаксический сахар»).  

Функциональность:  
- bash поддерживает массивы, расширенные конструкции условий (например, `[[ ... ]]`), 
  улучшенную арифметику, автодополнение и историю команд.  
- sh ограничен базовым набором команд стандарта POSIX. 
  В нем нет многих удобных инструментов Bash, что делает скрипты более простыми, но менее гибкими.  

Переносимость (Portability):  
- Скрипты на sh считаются максимально переносимыми: 
  они гарантированно запустятся на любой Unix-подобной системе (Solaris, BSD, разные дистрибутивы Linux).  
- Скрипты на Bash требуют наличия установленного Bash, который есть не везде
  (например, его часто нет в минимальных образах Docker или встраиваемых системах)  
  <mark>Примечание: bash доступен из коробки на ubuntu и astra-linux</mark>   

| Функция                | Синтаксис sh (POSIX)   | Синтаксис Bash           |
| ---------------------- | ---------------------- | ------------------------ |
| **Шебанг**             | `#!/bin/sh`            | `#!/bin/bash`            |
| **Массивы**            | Не поддерживаются      | `arr=(1 2 3)`            |
| **Условия**            | `[ "$a" = "$b" ]`      | `[[ $a == $b ]]`         |
| **Циклы (диапазон)**   | `for i in 1 2 3; do`   | `for i in {1..10}; do`   |

Для bash и sh стандратом является UTF-8 без BOM, с окончанием строк LF  
- Использование BOM создаст проблемы с шебангом.  
- Использование CRLF поломает скрипты (ошибка: лишний символ `\r`)  
<br/>


cmake
-----
Рекомендуемые настройки: UTF-8 без BOM, LF  

- BOM может вызвать проблемы у парсеров на старых Linux-системах или в специфических окружениях сборки.  
- Если вы используете CMake для сборки под Linux (через тот же Remote Build в VS), файлы с LF гарантируют, 
  что сгенерированные скрипты и команды не будут содержать лишних символов `\r`, 
  которые ломают сборку (как мы обсуждали ранее для Post-Build Event

Visual Studio
-------------

Проблема с LF:  

- Visual Studio — «верный подданный» Windows, и по умолчанию хочет видеть CRLF. 
  Как только вы измените что-то в настройках проекта через интерфейс (Property Pages), 
  VS может принудительно пересохранить файл, вернув в него CRLF.  


Проблема с UTF-8 без BOM:  

- Для `.vcxproj` и `.props` это работает (так как это XML), но до первого сбоя автоопределения. 
  Если кириллица попадёт в атрибуты, которые считываются до парсинга кодировки, возможны ошибки.  
- Для `.sln` это не XML файл. В нём нет строки `encoding="utf-8"`. 
  Без BOM Visual Studio откроет его в системной кодировке (1251), 
  и если там есть русские буквы, решение просто развалится.  

<a name="editorconfig"></a>
Общая рекомендация:  

- Для всех файлов (`.sln`, `.vcxproj`, `.props`, .`csproj`) используйте UTF-8 с BOM (Signature).  

- Cоздайте в корне проекта файл `.editorconfig`, 
  чтобы зафиксировать это поведение для всей команды и самой IDE:  

  ```
  # эта настройка говорит парсеру, 
  # что данный файл .editorconfig, это - главный файл настроек,
  # и не нужно искать другие файлы .editorconfig в папках выше по дереву.
  root = true
  
  # --- Стандартные настройки для всех файлов
  [*]
  charset = utf-8
  indent_style = space
  indent_size = 4
  insert_final_newline = true
  trim_trailing_whitespace = true
  
  # --- Проекты и файлы свойств (BOM для кириллицы в путях/настройках, LF для Remote Build)
  [*.{vcxproj,props,targets,csproj}]
  charset = utf-8-bom
  end_of_line = lf

  # --- Скрипты Linux (КАТЕГОРИЧЕСКИ без BOM, иначе сломается #!/bin/bash)
  [*.{sh,bash,py,cmake}]
  charset = utf-8
  end_of_line = lf

  [CMakeLists.txt]
  charset = utf-8
  end_of_line = lf
  
  # -- Решение Visual Studio (Windows-only, поэтому CRLF)
  [*.sln]
  charset = utf-8-bom
  end_of_line = crlf
  
  # --- Исходный код (BOM для кириллицы в комментариях и строках, LF для совместимости)
  # --- Современные GCC и Clang на Linux отлично переваривают BOM.
  [*.{cpp,c,h,hpp,cs}]
  charset = utf-8-bom
  end_of_line = lf
  ```

gitattributes
-------------
Файл: `.gitattributes`

```
# По умолчанию Git сам определяет текстовые файлы
* text=auto

# Явно указываем, что исходники и проекты — это текст, 
# и в репозитории они должны храниться с LF
*.cpp      text eol=lf
*.h        text eol=lf
*.vcxproj  text eol=lf
*.props    text eol=lf
*.sh       text eol=lf
*.py       text eol=lf

# Для .sln можно оставить CRLF даже в репозитории
*.sln      text eol=crlf

# Бинарные файлы (картинки, библиотеки) не трогаем
*.png      binary
*.jpg      binary
```

Параметр: `core.autocrlf`  
Каждый разработчик в команде должен настроить свой локальный Git.  
Для Windows-разработчиков, использующих Visual Studio, стандарт таков:  

```bat
git config --global core.autocrlf true
```

Как это работает:  
 - когда вы скачиваете код (checkout), Git превращает LF в CRLF, чтобы Windows было удобно.  
 - когда вы отправляете код (commit), он превращает всё обратно в LF.  

Но! Если у вас в `.editorconfig` жестко прописано `end_of_line = lf`, то Visual Studio сама будет сохранять файлы с LF.  
В этом случае Git увидит, что файл уже в LF, и ничего менять не будет.
